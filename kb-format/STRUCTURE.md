# sem-ai-kb Structure Guide — How to Reproduce for Other Documents

This guide describes the **internal schema of every file and component** in the

`sem-ai-kb` knowledge base, so you can reproduce the same structure for any new

document (another user manual, a policy bundle, an API doc, etc.).

---

## 1. Root Files

### 1.1 `AGENTS.md` — Agent Behavior Instructions

**Purpose:** Tells the AI agent how to behave when using this KB.

**Structure (line-by-line):**

```markdown
# <Product Name> assistant
You are an interactive guide for **<Product Name>**, a <short description>.
Your knowledge base is this folder (the manual, restructured). You are a guide,
not a search box: **interview first, then walk the user through, step by step.**
## How to use the KB
- If the MCP server is connected → use its tools (kb_start, kb_answer, kb_search, ...)
- Otherwise read files directly: index.md, interaction/decision-tree.json,
  modules/<module>/README.md, modules/<module>/<NN>-<section>.md, needs-review.md
## Core behaviour: clarify before answering
1. When a request is vague → ask 1-2 clarifying questions with 2-5 options + "something else"
2. Facts that change the answer → establish before giving steps (task type, framework, data layout)
3. Reuse what the user already told you. Never re-ask.
4. After interview → say what you understood in one line → ask follow-ups → proceed
## Core behaviour: guided walkthrough
- Present one step at a time → confirm before continuing
- Offer the next logical step when a step finishes
- If stuck → ask what they see on screen, which step, what they clicked
## Images
- Include screenshot path as `Screenshot: <path>` when relevant
- Don't dump every image; pick the one matching the current step
## Grounding rules
- Cite the source: *(Module Name, p. N)*
- If the manual doesn't say → say so. Never invent UI labels, values, defaults.
- Check needs-review.md before asserting values
- OCR slips can be read charitably but say when you do
## Maintenance
- modules/ is generated by tools/build-kb.js (rebuilding overwrites edits)
- needs-review.md is hand-maintained and never overwritten
- Edit interaction/decision-tree.json to change clarifying questions
```

**Key design rules:**

- Written in **second person** ("You are…", "Ask the user…")
- Specifies **when to interview vs answer directly**
- Defines **citation format** and **image inclusion rules**
- References the **maintenance workflow** (which files are auto-generated vs hand-maintained)

### 1.2 `README.md` — Setup Guide

**Purpose:** Tells a developer how to wire this KB into an agent harness.

**Structure:**

```markdown
# <repo-name>
Interactive knowledge base for **<Product Name>**, built from the user manual.
Works with any agent harness, with or without MCP.
## Option A: files only (any harness)
Point the harness at this folder and make `AGENTS.md` its instructions.
(For Claude Code: add CLAUDE.md containing `@AGENTS.md`)
## Option B: MCP server (recommended)
Zero dependencies, needs Node 18+. Use absolute path to `mcp-server/server.mjs`.
<JSON config examples for Claude Code, opencode, Hermes>
## Layout
<brief directory tree with descriptions>
```

---

### 1.3 `index.md` — Module Index

**Purpose:** Human-readable table of contents. Maps each module to its page range.

**Schema:**

```markdown
# <Product Name> knowledge base
Start with [AGENTS.md](AGENTS.md). Interview flow: [interaction/decision-tree.json](interaction/decision-tree.json).
## Modules
- [Module Title](modules/<module-slug>/README.md) — pp. START–END
- [Module Title](modules/<module-slug>/README.md) — pp. START–END
...
```

**Rules:**

- One bullet per module, in manual page order
- `<module-slug>` = lowercase, hyphenated, matches the folder name in `modules/`
- Page range = `[first_page, last_page]` from the source document

---

### 1.4 `needs-review.md` — Gap Tracker

**Purpose:** Hand-maintained list of known gaps (TBD values, OCR errors, undescribed images).

The agent reads this **before asserting any value**.

**Schema:**

```markdown
# Needs review
Auto-detected gaps in the manual (OCR slips, TBD values, image-only sections).
Edit this file as gaps are resolved; the agent reads it before asserting values.
- **<module>/<section-file>** (p. N): <description of the gap>
- **<module>/<section-file>** (pp. N–M): value not documented (TBD) — `<field>: <value>`
...
```

**Rules:**

- One bullet per gap
- Format: `**<module-slug>/<section-filename>** (p. N): <description>`
- Never overwritten by the build script
- A fresh OCR scan goes to `needs-review.generated.md` (not this file)

## 2. `interaction/decision-tree.json` — Clarifying Interview

**Purpose:** A JSON state machine that routes user intent to the correct module(s).

**Top-level schema:**

```json
{
  "start": "<node-id of the first question>",
  "nodes": { "<node-id>": { ... } },
  "resolve": { "<task>:<framework>": "<result-id>" },
  "results": { "<result-id>": { ... } }
}
```

### 2.1 Node object

```json
"<node-id>": {
  "ask": "The question text shown to the user",
  "why": "Optional explanation of why this question matters",
  "options": [
    {
      "label": "Short option text",
      "set": { "task": "classification" },     // optional vars to set
      "next": "<next-node-id>"                  // or "result:<result-id>"
    },
    { "label": "...", "next": "..." }
  ]
}
```

**Fields:**

| Field | Type | Required | Description |
|---|---|---|---|
| `ask` | string | ✅ | The question shown to the user |
| `why` | string | ❌ | Context for the agent (not shown to user) |
| `options` | array | ✅ | 2–5 choices + optional "something else" |
| `options[].label` | string | ✅ | Short label for the option |
| `options[].set` | object | ❌ | Key-value vars to accumulate (e.g. `{"task": "seg"}`) |
| `options[].next` | string | ✅ | Next node-id, or `"result:<id>"`, or `"resolve"` |

### 2.2 Resolve table

When `next` = `"resolve"`, the engine looks up `"<task>:<framework>"` to find the result-id:

```json
"resolve": {
  "single-x:tf": "single-x",
  "single-x:pt": "single-x-pt",
  "single-x:unknown": "single-x",
  "seg-binary:tf": "seg",
  "seg-binary:pt": "seg-pt"
}
```

**Pattern:** `"<task-value>:<framework-value>"` → `"<result-id>"`

### 2.3 Result object

```json
"<result-id>": {
  "modules": ["module-slug-1", "module-slug-2"],
  "summary": "One-line description of what this maps to",
  "start_hint": "Optional hint for which section to start reading",
  "ask_next": [
    "Follow-up question 1 to ask the user conversationally",
    "Follow-up question 2"
  ]
}
```

**Fields:**

| Field | Type | Required | Description |
|---|---|---|---|
| `modules` | string[] | ✅ | Module slugs (folder names in modules/) to load |
| `summary` | string | ✅ | One-line description shown to the user |
| `start_hint` | string | ❌ | Section heading to start from |
| `ask_next` | string[] | ❌ | Conversational follow-up questions |

**Design rules:**

- Start broad (goal: install, train, annotate, scale, explore)
- Branch by task type → sub-type → framework
- Each terminal result maps to 1–3 modules
- Follow-up questions are asked conversationally, not as buttons

## 3. `modules/` — Content Directory

### 3.1 Module folder: `modules/<module-slug>/`

**Naming:** `<module-slug>` = lowercase, hyphenated, matches the `id` in `kb.json`

(e.g., `single-x-classification`, `pytorch-segmentation`)

**Contents:**

```
modules/<module-slug>/
├── README.md          ← Module overview + section list
├── 01-<section>.md    ← First section
├── 02-<section>.md    ← Second section
├── 03-<section>.md
└── ...
```

**Section file naming:** `NN-<section-name-slug>.md`

- `NN` = two-digit zero-padded sequence number (01, 02, … 83)
- `<section-name-slug>` = lowercase, hyphenated, derived from the section heading in the manual

---

### 3.2 Module README: `modules/<module-slug>/README.md`

**Schema:**

```markdown
# <Module Display Title>
_Manual pp. START–END_
Sections:
- [SECTION HEADING](01-<section-slug>.md) — pp. N–M
- [SECTION HEADING](02-<section-slug>.md) — p. N
- [SECTION HEADING](03-<section-slug>.md) — pp. N–M
...
```

**Rules:**

- Line 1: `# <Title>` (human-readable, from the manual)
- Line 2: `_Manual pp. START–END_` (italicized page range)
- Blank line
- `Sections:` heading
- One bullet per section file, in order
- Each bullet: `[SECTION HEADING](NN-<slug>.md) — pp. N–M` (or `p. N` for single page)
- Link text = the actual heading from the manual (ALL CAPS if that's how it appears)

---

### 3.3 Section file: `modules/<module-slug>/NN-<section-slug>.md`

**Schema:**

```markdown
---
id: <module-slug>/<NN>-<section-slug>
module: <module-slug>
title: "<Section Heading>"
pages: [START, END]
---
# <Section Heading>
_Manual pp. START–END_
<body text — OCR'd from the manual, with screenshot references>
![screenshot p.N](../../images/page_NNN_imgK.png)
Image path: images/page_NNN_imgK.png
<more body text>
```

**YAML frontmatter fields:**

| Field | Type | Description |
|---|---|---|
| `id` | string | `<module-slug>/<NN>-<section-slug>` — unique across the KB |
| `module` | string | `<module-slug>` — matches the parent folder |
| `title` | string | The section heading from the manual (in quotes) |
| `pages` | [int, int] | `[start_page, end_page]` from the source document |

**Body rules:**

- Line after frontmatter: `# <Section Heading>` (same as `title`)
- Next line: `_Manual pp. START–END_` (italicized)
- Body = OCR'd text from the manual, preserving the original structure
- **Bold** marks UI labels and button names (e.g., `**Add Folder**`, `**Train**`)
- Screenshots embedded as:

```markdown
![screenshot p.N](../../images/page_NNN_imgK.png)
Image path: images/page_NNN_imgK.png
```

- The `../../images/` path is relative from `modules/<module-slug>/`
- `page_NNN` = zero-padded 3-digit page number
- `imgK` = image index on that page (1-based: img1, img2, img3…)

## 4. `kb.json` — Machine-Readable Index

**Purpose:** Single JSON file consumed by the MCP server for search and retrieval.

**Top-level schema:**

```json
{
  "modules": [ ... ],
  "sections": [ ... ]
}
```

### 4.1 `modules` array

```json
{
  "modules": [
    {
      "id": "single-x-classification",
      "title": "Single X Classification",
      "pages": [21, 28]
    },
    {
      "id": "segmentation",
      "title": "Segmentation (binary and multi-class, data annotation tools)",
      "pages": [58, 77]
    }
  ]
}
```

**Module object fields:**

| Field | Type | Description |
|---|---|---|
| `id` | string | Module slug (matches `modules/<id>/` folder) |
| `title` | string | Human-readable title |
| `pages` | [int, int] | `[start_page, end_page]` from the source |

### 4.2 `sections` array

```json
{
  "sections": [
    {
      "id": "single-x-classification/01-single-x-classification",
      "module": "single-x-classification",
      "title": "SINGLE X CLASSIFICATION",
      "pages": [21, 23],
      "images": [
        "images/page_021_img1.png",
        "images/page_022_img1.png",
        "images/page_022_img2.png",
        "images/page_023_img1.png",
        "images/page_023_img2.png"
      ],
      "file": "modules/single-x-classification/01-single-x-classification.md",
      "text": "About Here we perform classification on a single image..."
    }
  ]
}
```

**Section object fields:**

| Field | Type | Description |
|---|---|---|
| `id` | string | `<module-slug>/<NN>-<section-slug>` — unique |
| `module` | string | Parent module slug |
| `title` | string | Section heading (from YAML frontmatter) |
| `pages` | [int, int] | `[start_page, end_page]` |
| `images` | string[] | Relative paths to screenshots (`images/page_NNN_imgK.png`) |
| `file` | string | Relative path to the `.md` file (`modules/<module>/<file>.md`) |
| `text` | string | Full plain-text content of the section (no markdown, no frontmatter) — used for BM25 search |

**Key rules:**

- `text` = the body text with markdown stripped (bold markers removed, image lines removed) — this is what the search engine indexes
- `images` array lists every screenshot referenced in that section
- `file` path is relative to the KB root
- The `sections` array is ordered by module, then by section number

## 5. `mcp-server/server.mjs` — MCP Server

**Purpose:** Zero-dependency Node.js MCP server (stdio, JSON-RPC) that exposes KB tools.

### 5.1 Architecture

```
server.mjs
  │
  ├── Loads kb.json → builds BM25 search index
  ├── Loads interaction/decision-tree.json → interview engine
  │
  ├── Tool: kb_start        → returns first question from decision tree
  ├── Tool: kb_answer       → processes user's choice → next question or result
  ├── Tool: kb_search       → BM25 keyword search across all sections
  ├── Tool: kb_list_modules → lists all modules
  ├── Tool: kb_get_module   → lists sections in a module
  ├── Tool: kb_get_section  → returns full markdown + image paths for a section
  ├── Tool: kb_needs_review → returns needs-review.md content
  │
  └── JSON-RPC over stdio   → handles initialize, tools/list, tools/call, ping
```

### 5.2 BM25 search index (built at startup)

```javascript
// Stopwords removed, tokens lowercased
const STOP = new Set('a an the of to in is are and or for on with how do i can what...');
const tok = s => (s.toLowerCase().match(/[a-z0-9]+/g) || []).filter(w => !STOP.has(w));
// Each section → token array from: title + title + module-name + text
const docs = kb.sections.map(s => ({
  s,                                    // section object
  t: tok(`${s.title} ${s.title} ${s.module.replace(/-/g, ' ')} ${s.text}`)
}));
// Standard BM25 with k1=1.2, b=0.75
// Score = IDF * TF * (k1+1) / (TF + k1 * (1 - b + b * docLen/avgDocLen))
// IDF = log(1 + (N - DF + 0.5) / (DF + 0.5))
```

**To reproduce:** The search indexes `title` (doubled for weight), `module` name (hyphens → spaces), and `text` field from each section in `kb.json`.

### 5.3 Interview engine

```
kb_start() → nodeView(tree.start, {vars:{}, history:[]})
  → returns: { status:"question", question, options[], state }
kb_answer(state, option_index) →
  → reads state.node → gets option → applies opt.set to vars → follows opt.next
  → if next = "resolve" → looks up resolve[task:fw] → resultView()
  → if next = "result:X" → resultView("X")
  → else → nodeView(next)
resultView(rid) →
  → loads tree.results[rid]
  → fetches sections from kb.json for each module in results.modules
  → returns: { status:"result", summary, modules, follow_up_questions, sections[] }
```

### 5.4 Tool schemas

| Tool | Input | Returns |
|---|---|---|
| `kb_start` | (none) | First question + options + state object |
| `kb_answer` | `state` (object), `option_index` (int) | Next question OR result with modules/sections |
| `kb_search` | `query` (string), `limit` (int, default 5) | Ranked sections with excerpt (300 chars) + image paths |
| `kb_list_modules` | (none) | Array of `{id, title, pages}` |
| `kb_get_module` | `module` (string) | Module info + list of sections with `{id, title, pages, image_count}` |
| `kb_get_section` | `id` (string) | Full markdown text + image paths (relative & absolute) + original page scan paths |
| `kb_needs_review` | (none) | Content of needs-review.md |

## 6. `images/` — Screenshot Directory

**Naming:** `page_NNN_imgK.png`

- `NNN` = zero-padded 3-digit page number (014, 015, … 300)
- `K` = 1-based image index within that page (img1, img2, img3…)

**Source:** Cropped from the original page scans by the build script.

**Referenced by:**

- Section `.md` files (as `![screenshot p.N](../../images/page_NNN_imgK.png)`)
- `kb.json` `sections[].images[]` array (as `images/page_NNN_imgK.png`)

---

## 7. `pages/` — Original Page Scans

**Naming:** `page_NNN.jpg`

- `NNN` = zero-padded 3-digit page number

**Purpose:** Full-page scans of the source document. Referenced by `kb_get_section` tool as `original_page_scans`.

## 8. Reproduction Checklist

To build a KB for a **new document**, follow this order:

### Step 1 — Plan modules

- Read the source document's table of contents
- Group chapters into modules (each module = one folder in `modules/`)
- Assign page ranges

### Step 2 — Create the folder structure

```
<new-kb>/
├── AGENTS.md
├── README.md
├── index.md
├── needs-review.md
├── interaction/
│   └── decision-tree.json
├── modules/
│   └── <module-slug>/
│       ├── README.md
│       └── NN-<section-slug>.md
├── images/
├── pages/
├── kb.json
└── mcp-server/
    └── server.mjs
```

### Step 3 — Extract content

- OCR or parse the source document page by page
- Split into sections per module (one `.md` file per section)
- Add YAML frontmatter (`id`, `module`, `title`, `pages`)
- Crop screenshots → save to `images/page_NNN_imgK.png`
- Save full page scans → `pages/page_NNN.jpg`

### Step 4 — Build `kb.json`

- `modules[]` array: one entry per module with `{id, title, pages}`
- `sections[]` array: one entry per section file with `{id, module, title, pages, images[], file, text}`
- `text` = body content with markdown stripped

### Step 5 — Design the interview

- Write `interaction/decision-tree.json`:
  - Start node = broad goal question
  - Branch by task type → sub-type → framework/variant
  - Each result → module(s) + summary + follow-up questions

### Step 6 — Write agent instructions

- `AGENTS.md` — behavior rules (interview-first, walkthrough, grounding, citation)
- `README.md` — setup guide (files-only vs MCP server)

### Step 7 — Copy the MCP server

- Copy `mcp-server/server.mjs` (zero dependencies, only needs `kb.json` + `decision-tree.json`)
- It auto-loads from the parent directory

### Step 8 — Track gaps

- `needs-review.md` — hand-maintain TBD values, OCR slips, undescribed images

## 9. Quick Reference — All File Schemas

| File | Format | Key Fields |
|---|---|---|
| `AGENTS.md` | Markdown | Behavior rules, citation format, image rules |
| `README.md` | Markdown | Setup instructions, MCP config examples |
| `index.md` | Markdown | Module list with page ranges |
